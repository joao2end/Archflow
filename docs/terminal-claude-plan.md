# Terminal do Claude Code no modo agents

> Plano e backlog do loop (`docs/TERMINAL_LOOP_PROMPT.md`). Marque `[x]` + 1–3 linhas ao concluir cada tarefa.

## Objetivo
Abrir o `claude` (Claude Code) num terminal dentro do Archflow, no navegador (`npm run bridge`/Vite) e no app Electron,
com a pasta do projeto como `cwd`, para executar prompts contra o harness gerado (`.claude/agents`, `.mcp.json`).

## Decisões fechadas (não reabrir)
- Terminal real: PTY (`node-pty`) no bridge + `xterm.js` na UI, ligados por WebSocket. Sem chat headless.
- Funciona nos dois ambientes (navegador e Electron); o mesmo código do bridge.
- Segurança: WebSocket só de mesma origem + token do boot (`GET /api/term/info`); POST com header `x-archflow-term`;
  só `claude` ou shell do usuário, em argv (sem interpolar em shell); só loopback (`ARCHFLOW_TERM=1` assume o risco); nada no modo público.
- Nunca usar `--dangerously-skip-permissions`. O `claude` usa a autenticação do usuário.
- O `prefill` do prompt é digitado no terminal SEM Enter; o usuário confirma.

## Decisões novas (pedido do usuário, 2026-10-15)
No modo agents deve existir um **modo de execução de prompts** que abre o terminal, e dá para **cadastrar prompts** e **executar um workflow** com eles.
- **Prompt cadastrado**: `{ id, name, text, agent?, notes? }`. `agent` (opcional) é o nome de um subagente do diagrama: ao executar, o texto vai prefixado por «Use o subagente <agent> para: ». Variáveis `{{nome}}` no texto, preenchidas num formulário antes de executar.
- **Onde ficam**: no projeto, em `.archflow/prompts.json` (versionável, fora do diagrama e fora do harness gerado). Rotas `GET/PUT /api/prompts` no bridge, com validação pura em `src/shared/prompts.ts`.
- **Workflow**: lista ordenada de passos `{ promptId, mode }` com nome, também em `.archflow/prompts.json`. Dois modos de execução:
  - **Manual (padrão)**: uma sessão interativa do `claude`; cada passo é digitado no terminal SEM Enter e o usuário confirma; botão «Próximo passo» avança. Mantém o contexto da conversa entre passos.
  - **Automático**: cada passo roda `claude -p "<texto>" --session-id/--resume <uuid>` num PTY e o runner espera o processo sair (código 0) antes do próximo; para no primeiro erro. Permissões seguem o `claude` normal (sem `--dangerously-skip-permissions`); passo que pedir permissão fica visível no terminal e o usuário responde.
- O runner é uma máquina de estados pura em `src/shared/workflow.ts` (testável sem PTY); a UI e o bridge só a alimentam.

## Pós-T13 (2026-10-15/16): conversa compartilhada e revisão da interface

- **Conversa compartilhada (pedido do usuário):** todos os passos de um workflow, manuais e automáticos, usam a mesma conversa (`sessionId` da execução). Confirmado com o claude real: um `claude -p --session-id U` seguido de `claude --resume U` interativo enxerga o que o `-p` guardou, e o `-p --resume U` seguinte enxerga o que foi dito no interativo (mesmo depois de matar o processo). `shared/workflow.ts`: o efeito `type` agora leva `sessionId`/`first`; `first` = nenhum passo anterior concluído (manual ou automático) nem automático que chegou a rodar; pular não conta. `server/terminal.ts`: `sanitizeClaudeArgs` aceita também o formato interativo `(--session-id|--resume) <uuid> [--permission-mode …]` (o texto vai em `prefill`). UI (`workflow.tsx`): passo manual abre aba interativa `--session-id` (1º) ou `--resume`; manuais seguidos reaproveitam a aba; antes de um automático a aba interativa é fechada (+0,7 s para o claude gravar) para nunca haver dois processos na mesma conversa. Validado no navegador com claude falso: manual `--session-id U` → auto `-p --resume U` → manual `--resume U` (texto digitado) → auto `-p --resume U`, tudo com o mesmo id. Limite resolvido depois: `GET /api/term/conversation?id=` (`conversationExists`, confere `<config>/projects/*/<id>.jsonl`, que só nasce na 1ª mensagem; verificado com o claude real) — o workflow usa `--session-id` quando a conversa ainda não existe (ex.: manual concluído sem enviar nada) e `--resume` quando existe.
- **Revisão da interface** (skills design-critique e frontend-design, dentro da identidade existente do app): um aviso por vez no painel (prioridade erro > claude ausente > harness velho > resultado do sync > dica do trust; a dica sai para sempre ao dispensar e só aparece em sessões com texto a digitar); cabeçalho com `+` (Claude Code) e `▾` (shell), contador só perto do limite; barra lateral em dois níveis (lista com ▶ de execução direta → editor), um botão principal (Executar), detalhes sob demanda (subagente, notas, permissões), ações raras em «⋯»; destino «Sessão atual/Nova sessão» só aparece quando há aba claude viva; passos com alternância Manual|Auto; cartão de execução em tela própria com só os botões que fazem sentido no estado; títulos de aba curtos («Entrega · 2/4»). Novos: `src/ui/panekit.tsx` (`MoreMenu`, `PaneHead`). CSS do painel reescrito (classes `.tseg`, `.pane-*`, `.term-note`), escopado para não colidir com `.seg`/`.btn.sm` do app.
